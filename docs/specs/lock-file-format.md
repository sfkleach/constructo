# The lock file

> **Status:** this is the design for Step 4 of the projects task (`docs/tasks/2026-10-21-projects/projects.md`). It is
> not implemented yet, so `constructo check` does not read a lock file and there is no `constructo project update`.
> This document is the specification that the implementation is built to, and it is changed with it.

A project that imports other projects records a digest of each of them in a lock file, so that a dependency cannot
change without being noticed. The lock file is `constructo.lock`. It sits next to `constructo.toml` in the root of the
project that `constructo check --project=FOLDER` is run on. It is written by `constructo project update` and by nothing
else. `constructo check` never changes any file.

## What it records

The lock has one entry for each project that is loaded, other than the root project and the built-in projects.

- The lock covers the whole closure of imports, direct and indirect. Imports are not transitive for names but they are
  for loading, and a change deep in the graph must still be caught. The lock files of the imported projects are ignored.
- The root project is not recorded, because its files are the ones that are being edited.
- A built-in project, such as `constructo.prelude`, is not recorded, since it has no files on disk and its content is
  fixed by the binary.
- The source of a project is not recorded. Different importers may write the same project with different paths.
- A project that imports only built-in projects has nothing to record and needs no lock file.

An entry covers the files that the project's `include` and `exclude` patterns select, and its `constructo.toml`.
Including the project-file means that a change to what a dependency imports, or to its patterns, is noticed. Values
files, notes and any other files in the folder are not covered.

## Format

The file is [TOML](https://toml.io), in UTF-8 with no byte order mark, ended by a newline. It is generated, and it is
written so that it does not change unless the content does: the projects are sorted by name and the files by path.

```toml
# This file is generated by `constructo project update`. Do not edit it.
version = 1

[[project]]
name = "com.example.lib"
digest = "sha256:753517eedcd17f9bae3699b7e6b2a1be5f91f4e382a3d80de5f0f59ebdc5b163"

[project.files]
"constructo.toml" = "sha256:1cfdac805747c77556236b673fc4fb71a344aa39d1f8dfdb37bf53fbfae70830"
"shapes/circle.types" = "sha256:1b0ecdd124592b686f69f8d4544f644fa34b2732bdb94e0500eda45c77025346"
```

| Key                  | Type   | Meaning                                                                    |
|----------------------|--------|----------------------------------------------------------------------------|
| `version`            | int    | The version of the format. It is `1`.                                      |
| `[[project]]`        | table  | One for each recorded project.                                             |
| `name`               | string | The full name of the project. It is unique in the file.                    |
| `digest`             | string | The digest of the project, as below.                                       |
| `[project.files]`    | table  | The digest of each file, keyed by its path inside the project, with `/`.   |

The file is strict. These are errors, with a line and column in `constructo.lock`, and the exit code is 2, as for the
project-file:

- an unknown key, a missing `version`, `name`, `digest` or `files`, and a value of the wrong type;
- a `version` other than 1;
- a project name that does not follow the rule for a project name, and a project that is in the file twice;
- a digest that is not well-formed: `sha256:` and 64 lowercase hexadecimal digits;
- a file path that is empty, has a `\`, or is not relative to the project, with an empty part, `.` or `..`;
- a project `digest` that is not the digest of the files that are listed for it. It is worked out from them, so only
  an edit by hand can make it differ, and the message says the lock file was edited. Without this check an edit would
  show up as a mismatch for a file that has not changed.

## The digests

A digest is written `ALGORITHM:HEX`, where the algorithm is named so that it can be changed later. The only algorithm
is `sha256`, and the hexadecimal digits are lowercase.

### A file

The digest of a file is the SHA-256 of the file's bytes after

1. a byte order mark at the start of the file, if there is one, has been removed, and
2. each CRLF (the bytes `0D 0A`) has been replaced with a LF (`0A`).

A lone CR is left alone. The byte order mark is removed from every file that `constructo` reads, as `rustc` does for a
source file, and the digest is of what is left. So a project that is checked out on Windows with CRLF files matches a
lock that was made on Linux, and so does one that was saved by an editor that adds a byte order mark.

### A project

The digest of a project is the SHA-256 of a text built from its files. For each file, in order of path, the text has
a line

```text
PATH DIGEST
```

where `PATH` is the path of the file inside the project, written with `/`, and `DIGEST` is the digest of the file,
including the `sha256:`. Every line ends with a LF, including the last, and there is one space between the two parts.
The paths are sorted by their bytes in UTF-8. The digest depends only on the paths and the contents of the files, so it
is the same wherever the project is, and it is a quick check and a single value to quote.

### A worked example

Take a project `com.example.lib` with these two files, where the second is saved with CRLF line endings.

`constructo.toml`:

```toml
[project]
name = "com.example.lib"
```

`shapes/circle.types`:

```text
enum Shape = Circle;
const unit: Shape = Circle;
```

The digests of the files are those of the text with LF line endings. The SHA-256 of `shapes/circle.types` as it is on
disk, with CRLF, would be `sha256:197363586e7f...` and is not what is recorded.

| File                  | Digest                                                                      |
|-----------------------|-----------------------------------------------------------------------------|
| `constructo.toml`     | `sha256:1cfdac805747c77556236b673fc4fb71a344aa39d1f8dfdb37bf53fbfae70830`   |
| `shapes/circle.types` | `sha256:1b0ecdd124592b686f69f8d4544f644fa34b2732bdb94e0500eda45c77025346`   |

The text of the project is these two lines, each ended by a LF:

```text
constructo.toml sha256:1cfdac805747c77556236b673fc4fb71a344aa39d1f8dfdb37bf53fbfae70830
shapes/circle.types sha256:1b0ecdd124592b686f69f8d4544f644fa34b2732bdb94e0500eda45c77025346
```

and the digest of the project is `sha256:753517eedcd17f9bae3699b7e6b2a1be5f91f4e382a3d80de5f0f59ebdc5b163`. It can be
checked with `sha256sum`.

## Verification

`constructo check --project=FOLDER` verifies the lock after the projects have been loaded, and before anything is
type-checked. The problems are all reported, since each is an independent fact, and the exit code is 1.

- A file whose digest is not the one in the lock is an error. It names the project and the file, shows both values, and
  is at the entry in the lock file. The digest of a project is worked out from the digests of its files, so a project
  that has changed shows as the files that changed, and is not reported again as a whole:

  ```text
  ERROR: Checksum mismatch for shapes/circle.types of project com.example.lib: the lock has
  sha256:77e0... but the file has sha256:12ac... (constructo.lock, line 8, col 24)
  ```

- A loaded project that has no entry is an error at the `[[import]]` that loaded it. A file of a project that matches
  its patterns but is not in the lock is an error at the entry of the project.
- The lock must describe exactly what is loaded. A project in the lock that is not loaded, and a file in the lock that
  is no longer in the project, are errors at their entries.
- A project with nothing to record needs no lock file, and with none, nothing is verified. Any other project with no
  lock file is an error at its first import, which says to run `constructo project update`.
- A lock file that cannot be read, or that does not parse, is an error with exit code 2.
- `constructo check` without `--project` has no lock and verifies nothing.

The built-in projects are never verified.

### The option `--dev`

`-d, --dev` switches off all verification of the lock, for every project, and a missing lock file is then not an error.
It means "I am developing, trust what is on disk". It is a setting like the other boolean options: `dev` in the
`[check]` table of a [configuration file](config-file.md), with the negative form `--no-dev`, and it is shown by
`--print-config`.

## Updating the lock

`constructo project update [FOLDER]` writes the lock. `FOLDER` defaults to the current folder.

- It loads the project in the same way as `check` does, with the same strictness, and writes `constructo.lock` in the
  folder. It does not type-check anything.
- It prints one line for each difference from the old lock: a project or a file that was added, changed or removed,
  with the old and new digest. It prints nothing if the lock is already up to date.
- It does not need the old lock to be valid or to exist, since the point is to accept a change.
- A project with nothing to record gets no lock file, and an old one is removed so that it does not become stale.

The difference can be reviewed from the output of the command, or with `git diff constructo.lock`.
